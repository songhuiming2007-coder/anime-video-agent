一条把选题变成 2–4 分钟动漫二创成片的命令行流水线。输入是一句选题，输出是可以直接上传的
mp4、封面图和标题候选。中间的写稿、配音、找素材、剪辑、质检由脚本和 coding agent 完成，
人只在两个地方介入。

# 一、项目介绍

## 1.1 它做什么

给定一个选题（例如「八幡的自我牺牲其实是自我保护」），流水线依次完成：

```
选题 → 写稿 + 稿件机检 → 本地 TTS 配音 → 语义检索排画面 → [人审时间码]
     → 渲染（切片 + 烧字幕 + 混 BGM）→ 11 项自动质检 → 封面候选 + 标题 → [人选并发布]
```

每一步都是一条独立命令，产物落在同一个目录里并带序号：

```
data/episodes/2026-07-30-春物-雪乃适合大老师/
├── 01-topic.md              选题：模式、张力、锚点、封面集
├── 02-script.md             全稿 + 逐段分镜标注
├── 03-audio/                21 段配音 wav + manifest.json（每段真实时长）
├── 04-clips.json            排片结果（机器排的）
├── 04-clips.approved.json   人批准之后的版本，只有它能进渲染
├── 05-final.mp4             成片，188.7 秒
├── 06-check.log             质检报告，11 项
├── 07-titles.md             标题候选与定稿
├── 08-cover.jpg             封面，1920×1080
└── meta.md                  本期实际人类耗时
```

**看目录里有哪些文件，就知道进行到哪一步。** 没有数据库、没有状态文件、没有任务队列。
任何一步失败，修好之后从那一步接着跑，不用从头重来。

## 1.2 人在哪里出现

| 步骤 | 谁做 | 时长 |
|---|---|---|
| 周批量选题（摊到每期） | 人 | 1.5 分钟 |
| 写稿、配音、排片 | Agent | 约 6 分钟机器时间 |
| **05 审时间码** | **人** | **5 分钟** |
| 渲染、质检、封面 | Agent + 机器 | 约 2.5 分钟机器时间 |
| **09 选封面、选标题、上传** | **人** | **3 分钟** |

设计目标是人类每期投入 ≤ 10 分钟。超预算不当作「这期多花点时间」，而是当作流水线有 bug，
处理方式是改流水线或砍掉那个环节。

> 这个 9.5 分钟目前还没端到端验证过。第一期是边搭边做的，第二期在选题上反复返工，
> 花掉的人工远超预算——那部分不是流水线的问题，但账确实还没验成。

## 1.3 核心设计取向：让失败显式发生

这条流水线上几乎所有难修的 bug 都有同一个特征：**它不报错。**

- ffmpeg 截取片段超出源片末尾时，静默截断，返回 0
- 语义检索找不到合适画面时，照样返回 Top-K，分数照样在阈值以上
- 索引只建了 6 集而片源有 41 集时，检索照常工作，成片照常渲染
- TTS 把引号念成字时，回读质检判 PASS
- 字幕长到出画时，「原文长度 ÷ 每行容量」这个检查判 PASS

所以整个项目的重点不在功能，而在**判据**：每加一道检查，先问它测的是不是真实产物；
每引入一个分数，先问它能不能用来排序。第 3 节会在每一步里具体说明这些判据长什么样。

代码里几乎每个常量后面都跟着「为什么是这个数」，每个 workaround 后面都跟着
「不这么做会怎样」。`docs/adr/` 记的是难以回头的决策。

## 1.4 明确不做的事

- **不做纯搬运。** 混剪加原创口播属于灰区，口播是加分项；没有口播的内容不做。
- **不自动上传。** 省下的几分钟不值得拿账号冒险，第 09 步永远手动。
- **不做画质、转场、文案的无限打磨。** 边际收益极低，时间只花在让流水线更自动、更可靠上。
- **政治议题不进自动管道。** agent 不掌握中文平台的审核边界，风险显著高于人工。
- **不引入 NLE 和视频框架。** MoviePy 比直接调 ffmpeg 慢一个量级且不增加能力；
  Remotion 要等表现力真撞到天花板再说。

# 二、前置要求

## 2.1 运行环境

| 项目 | 要求 | 不满足会怎样 |
|---|---|---|
| **coding agent** | 能跑 shell、能读图 | 第 02 步写稿没有对应脚本，缺了它这一步就是空的。详见 2.2 |
| 操作系统 | macOS | 只在 macOS 上跑过 |
| **处理器** | **Apple Silicon**（配音与 ASR 需要） | Intel Mac、Linux、Windows 装不上 `mlx`，第 03 步配音和 ASR 兜底不可用；索引、排片、渲染、质检、封面都能正常跑 |
| Python | 3.12 / 3.13 / 3.14 | 3.15 还在 beta，没验过。**依赖里的 `numpy<2.5` 上界不能删**，理由见 2.6 |
| ffmpeg | 必须带 libass | 烧不了字幕，渲染会在最后一步失败。`brew install ffmpeg` 的默认版本带 |
| 包管理 | `uv` | 也可以用别的，但依赖版本是按 uv 那一组钉住的 |

语音部分只跑 Apple Silicon 是硬限制，不是配置问题。`config/voice.json` 留了 `engine`
字段作为接缝，换成云 API 或别的本地引擎只需要实现一个函数，但仓库里目前只有 mlx 一种实现。

## 2.2 coding agent 是前置要求，不是可选项

**这个仓库的预期用法是 clone 下来交给 coding agent 驱动**，不是一个人对着终端敲九条命令。
仓库里有两份东西专门写给 agent 看：

| 文件 | 给 agent 的内容 |
|---|---|
| `CLAUDE.md` | 工程约定：哪些判据不许绕过、哪些失败必须报出来、什么时候该停下来问人 |
| `skills/write-script/` | 写稿指令：形状与判据、节奏量化、`查询` 字段怎么写才检索得到 |

各步骤对 agent 的依赖程度不同，说清楚以免误会：

| 步骤 | 没有 agent 行不行 |
|---|---|
| 02 写稿 | **不行。** 没有任何脚本会生成稿子，`check_script` 只负责检查现成的稿子 |
| 01 选题 | 可以自己写 `01-topic.md`，agent 的作用是扫番剧笔记批量提候选 |
| 08 挑封面候选 | 可以。不加 `--pick` 会退到机械铺开取样，仍然出 9 张，只是不一定切题 |
| 08 写标题 | 脚本只抽原料（稿件的第 2、8 节），5 条候选由 agent 写 |
| 其余各步 | 都是纯脚本，跟 agent 无关 |

对 agent 的能力要求有两条是实的：**能跑 shell**（九步都是命令行），
**能读图**（第 08 步的第 2 层要看 6×5 的联系表认人、判断谁占主位）。
不能读图的 agent 仍然能跑完整条流水线，只是封面挑选退化成机械取样。

> 联系表这个设计本身就是为 agent 做的：把几百张候选拼成 6×5 的大图，
> 一张顶 30 次单张读取，纯粹为省 token。

## 2.3 需要的模型（合计约 4G）

模型全部落在 `data/models/` 下，不落系统盘。这一点由 `pipeline/paths.py` 在 import
时把 `HF_HOME` 钉到 `data/models/` 来保证。

| 模型 | 用途 | 大小 | 怎么来 |
|---|---|---|---|
| `BAAI/bge-base-zh-v1.5` | 字幕语义索引与检索 | 约 400M | 首次运行自动下载 |
| `mlx-community/whisper-large-v3-turbo` | 配音回读质检、字幕对轴校验、无字幕时兜底转录 | 约 1.5G | 首次运行自动下载 |
| IndexTTS-1.5（mlx 转换版） | 配音 | 约 1.3G | 手动放到 `data/models/local/IndexTTS-1.5/`，需要 `config.json`、`model.safetensors`、`model.safetensors.index.json`、`tokenizer.model` 四个文件。也可以把 `config/voice.json` 的 `model` 改成 HF 仓库名让它自动下载 |
| `deepghs/anime_face_detection` | 视觉索引：动漫人脸检测 | 约 42M | 首次运行自动下载 |
| `deepghs/ccip_onnx` | 视觉索引：角色身份嵌入 | 约 143M | 首次运行自动下载 |
| ~~`OFA-Sys/chinese-clip-vit-base-patch16`~~ | 视觉索引第 2 层（画面语义）——**探针没过，已决定不建，不需要下** | 约 750M | 见 ADR-0003 待实测 #4 |

> **注意 import 顺序。** 任何会下载模型的模块，第一个 import 必须是 `pipeline.paths`。
> `huggingface_hub.constants` 一旦被别的库先 import，缓存路径就定死成常量，
> 此后再设环境变量无效，模型会安安静静写进系统盘。`paths.py` 会检测这种情况并当场报错。

## 2.4 需要自备的素材

仓库不包含也不分发任何素材。

| 素材 | 要求 |
|---|---|
| 片源 | 一部番的完整正片。几十 G 量级 |
| 字幕 | **时间轴必须是照你手上那个视频文件打的。** 只允许三种来源：ffmpeg 从该文件提取的内封字幕；对该文件跑 ASR 转录的结果；与该文件同属一个发布、文件名逐一对应且通过对轴校验的外挂字幕 |
| 参考干声 | 5–8 条，每条 8–10 秒，连续说话不要留大段静音。用来克隆口播音色 |
| BGM | 该番自己的 OST / OP / ED。整轨镜像加 cue 的碟需要先分轨 |

**永远不要用第三方字幕文件配第三方视频文件。** 跨版本（BD 版字幕配 TV 版视频之类）的
差异是中间的插入与删除，不是恒定偏移，加 offset 修不好。而帧级精确截取是整条渲染链路的
前提，前提一塌，视频照样渲染出来，只是全程画面对不上话，没有任何报错。

## 2.5 `data/` 放在哪

仓库本身只有纯文本（代码、配置、文档、skills），全部进 git。片源、字幕、索引、模型、
每期产物都在 `data/` 下，不进 git。`data/` 放在哪由你定，两种放法都支持：

```bash
# 系统盘装得下，建实体目录
./pipeline/preflight.sh --init

# 系统盘装不下，在外置盘建骨架，data/ 做符号链接指过去
./pipeline/preflight.sh --init /Volumes/<你的盘>/anime-video-data
```

建出来的骨架：

```
data/
├── library/
│   ├── raw/<番>/<该季目录>/    片源
│   ├── subs/                  字幕
│   ├── index/                 台词向量索引（每集一个 .npy + 一个 .json）
│   ├── shots/                 镜头表 + 每镜头的代表帧
│   ├── vindex/                视觉索引：角色在场、画面语义、人脸簇
│   ├── bgm/<番>/              分轨后的 BGM
│   ├── notes/<番>.md          番剧笔记：可用集清单、名场面时间码、曲目表
│   └── sources.json           片源登记表，渲染时靠它找文件
├── models/                    模型权重
├── voice/reference/           参考干声
└── episodes/                  每期产物
```

**脚本绝不自动创建 `data/`，不可达就立刻报错退出。** 这条是刻意的：符号链接指向未挂载的
卷时，`mkdir -p data/library` 会在 `/Volumes/` 里建出实体目录，几十 G 静默写进系统盘，
而且那块盘插上之后你还看不见它（挂载点被占，系统改挂到「卷名 1」）。
所以建骨架必须是显式动作，`preflight.sh --init` 会打印结果落在哪块盘上。

代码里一律用 `./data/...` 相对路径，不硬编码卷路径——卷路径通常含空格，而且卷名会变。

## 2.6 安装

```bash
brew install ffmpeg
uv venv --python 3.14                         # 3.12 / 3.13 / 3.14 都可以
uv pip install -e ".[apple,dev]"              # 非 Apple Silicon 去掉 apple
pytest                                        # 273 条，不碰片源/模型/外置盘
./pipeline/preflight.sh                       # 自检
cp CLAUDE.local.md.example CLAUDE.local.md    # 填本机情况，不进 git
```

`pytest` 首次跑要一分钟左右（torch 第一次 import 慢），之后每次约 3 秒。

`preflight.sh` 检查四件事：`data/` 可达、ffmpeg 和 ffprobe 在、**ffmpeg 真的带
ass 滤镜**。最后一条单独检查是因为有 ffmpeg 不等于能烧字幕，缺了 libass 整条渲染会在
最后一步才失败。

`CLAUDE.md` 是给 coding agent 读的工程约定，跑这个项目的人也建议读一遍，
它解释了大量「为什么不那样做」。`CLAUDE.local.md` 放只对你这台机器、你这个账号成立的
事实（盘符、播放数据、优先级），不进 git。

### 关于 Python 版本和那条 `numpy<2.5`

2026-07-30 实测，**3.12、3.13、3.14 三个版本都跑通**（各 165 条测试全过，
外加 mlx 真做矩阵乘、numba 真做 JIT 编译）。3.15 还在 beta，没验，所以
`requires-python` 卡在 `<3.15`。

`pyproject.toml` 里那条 `numpy>=2.0,<2.5` 的上界**不能删**。依赖链是这样的：

```
mlx-whisper → numba → llvmlite
              └── numba 0.66 要求 numpy<2.5
```

numpy 2.5 发布之后（它的 `requires-python` 是 `>=3.12`，所以三个版本都拿得到），
解析器会优先选 numpy 2.5.1，于是 numba 0.66 被排除，一路回退到 numba 0.53.1——
那个版本的 llvmlite 0.36 只支持 Python `<3.10`，于是转去源码构建并失败。

> **这个坑只咬新环境。** 已经建好的 venv 是 numpy 2.5 发布之前装的，一切正常，
> 所以「我这儿能跑」完全不构成证据。这个仓库的 `requires-python` 原先写的是
> `<3.13`，理由写的是「部分 ML 包尚无对应 wheel」——那句话当初没验，而且是错的：
> 全部直接依赖都声明 `>=3.10`，没有一个有上界。真正的约束一直在 numpy 上，
> 而那个上界当时没写，**结果是照 README 装在 3.12 上也会失败**。
>
> 顺带一句：`uv pip install --dry-run` 在这里帮不上忙。它只解析、不构建，
> 所以它会「成功」地解出一个装不上的组合。判据得是真装一遍。

# 三、技术栈及全流程工作介绍

## 3.1 技术栈一览

| 环节 | 用什么 | 为什么这么选 |
|---|---|---|
| 语义检索 | `sentence-transformers` + bge-base-zh-v1.5，向量归一化后点积即余弦相似度 | bge-small 实测 Top-1 命中率只有 75%，base 是 100%（8 条查询）。不为省 300M 退回 small |
| 索引单元 | ASS 字幕滑窗 2 行，向量存 `.npy`，一集一个文件 | 单行太碎，一句话常跨两行轴；3 行开始混进无关对话 |
| 字幕解析 | `pysubs2` | ASS 的 style 名和 `\p1` 绘图标签都是关键信号，见 3.2 |
| 配音 | IndexTTS-1.5 跑在 `mlx-audio` 上，自回归解码循环自己写 | 云 API 会把「必须联网 + 有账号 + 有配额」塞进主循环，还要把参考干声传给第三方。上游 `generate()` 有两处 bug，见 ADR-0002 |
| ASR | `mlx-whisper` large-v3-turbo | 三处都用它：配音回读质检、字幕对轴校验、无字幕时兜底转录 |
| 视频与音频 | 全程 ffmpeg，无 NLE | 见 1.4 |
| 字幕烧录 | `ass` 滤镜（libass），折行自己算 | libass 靠空格找断点，中文整句没有空格就根本不折 |
| BGM | `sidechaincompress` 侧链闪避，每首按实测响度归一到 -26 LUFS | 固定音量系数是错的控制量，见 3.3 第 06 步 |
| 成片响度 | `loudnorm` 归一到 -16 LUFS，true peak 上限 -1 dBTP | 质检门禁按同一组数判 |
| 镜头切分 | ffmpeg `scdet`，一趟解码存下全部候选切点 | 检索单元必须是镜头不是帧——镜头和字幕单元同在一条时间轴上，天然可交。低阈值扫一遍再按判定阈值过滤，改阈值不用重解码 |
| 角色在场 | 动漫人脸检测（YOLOv8）→ CCIP 角色嵌入 → OPTICS 聚类 → 人工贴名 | booru tagger 那条捷径实测不够用：词表大的认不准、认得准的词表小，见 3.2 第三步 |
| 封面筛选 | `Pillow`：拉普拉斯方差 + 平均亮度 + dHash + 时间邻近去重，可选角色在场过滤 | 只做剔除，不做排序，见 3.3 第 08 步 |
| 状态管理 | 文件系统 | 产物即状态。人机交接一律走文件，不走对话上下文 |
| 测试 | `pytest`，273 条纯函数测试 | 不 mock ffmpeg 和模型，mock 检查的是 mock |

没有的东西也是选择：没有云 API、没有数据库、没有编排框架、没有 web 界面、没有一键脚本。

## 3.2 Phase 0：一部番做一次

Phase 0 的成本是固定的，跟你要做 1 期还是 10 期无关，所以只有摊到多期上才划算。
一部番要榨干再换番。

### 第一步：验片源完整性

```bash
python -m pipeline.ingest intact data/library/raw/<番>/*/*.mkv
```

**下载器显示 100% 不等于文件完整。** BT 没下完的文件是稀疏文件，文件头完好，
`ffprobe` 照样读得出时长，只有解到空洞处才出错。

判据是拿 ffmpeg 只解复用地走一遍全片（`-c copy -f null -`），任何报错即判残缺，
约 0.9 秒一个文件。

> 最初用的判据是「实占块 ÷ 逻辑大小 ≥ 99%」，后来推翻了。推翻依据是拿 qBittorrent 的
> piece 级 SHA-1 校验当真值，对 89 个 mkv 逐个比对：块比例判据漏放 14/72 个残缺文件，
> 最大高估 83 个百分点——一个真实只下了 16.7% 的文件读出 100.1%。成因是 piece 校验
> 失败后下载器只在逻辑上把该片标回缺失，磁盘上那些字节还留着。
> `ffmpeg` 判据漏放 0/72。块比例降级为前置快筛：它说「没下完」可信，说「下完了」不可信。

### 第二步：整季入库

```bash
python -m pipeline.ingest phase0 data/library/raw/<番>/<该季目录>/*.mkv \
    --anime <番> --season 1
```

这一条命令做三件事：逐集跑对轴校验 → 过了才建索引 → 把片源路径登记进 `sources.json`。
三步不许拆开只跑一两步。逐集打印结果，任何一集对轴不过就跳过它并说明原因，不静默降级。

换发布组要给两个参数：`--pattern`（从文件名取集号的正则，需含 `(?P<episode>…)`）和
`--sub-glob`（同名外挂字幕的通配符，默认 `*.Chs&Jap.ass`）。

**对轴校验怎么做的**：对视频抽几段跑 ASR，跟字幕在同一时间区间内的文本比字符错误率，
低于阈值才算对上。文件名对应只能证明「打包时放在一起」，证明不了轴没错，
真正能证伪的只有拿视频自己的声音去对。这一步需要字幕带日文轨——只有纯中文字幕的集
没有可比的东西，得走 ASR 兜底或者放弃。

> 这道校验曾经把正确的轴判成错的。原因是 Whisper 进了复读循环，输出「pada pada pada…」
> 让 CER 达到 1297%，脚本把「ASR 坏了」当成了「轴错了」。修法是输出长度超字幕 2 倍就
> 判该采样窗不可用，**跳过而不是记为反证**——门禁拿到的信息里没有能证伪的东西时，
> 应该跳过样本，不该定罪。

### 第三步：建视觉索引

字幕索引答的是「谁说了什么」，画面里有谁它答不了。这一步补上（设计见
[ADR-0003](docs/adr/0003-visual-index-as-filter.md)），一部番一次，机器时间约 2.4 小时：

```bash
# 1) 定镜头切分阈值。一部番一次，看两张抽检图再拍板，不许抄默认值
python -m pipeline.shots calibrate <一集视频>
python -m pipeline.shots calibrate <一集视频> --sheet 10    # 查过切
python -m pipeline.shots calibrate <一集视频> --long 10     # 查漏切
# 选定的数写进 config/project.json 的 visual.scene_threshold

# 2) 逐集切分并抽代表帧（约 2.2 分钟/集）
python -m pipeline.shots build <视频> --anime <番> --season N --episode M
python -m pipeline.shots frames <番> <集号>

# 3) 人脸检测 + 角色嵌入（约 1.3 分钟/集）
python -m pipeline.faces detect <番> <集号>...

# 4) 聚类，出联系表
python -m pipeline.faces cluster <番>
python -m pipeline.faces sheet <番>

# 5) ← 人在这里：看图给每簇贴名（实测 7 簇约 2 分钟）
python -m pipeline.faces name <番> 0 八幡

# 6) 落索引
python -m pipeline.faces presence <番>
```

第 5 步的人工介入**是设计的一部分，不是妥协**：一部番只做一次，与音色、BGM 曲目表、
番剧笔记同属 Phase 0 资产；而姐妹脸这类只有人能一眼分开。

> **为什么不用现成的 booru tagger 省掉聚类和贴名。** 试过，三个都不够用：
> 词表最大的 camie（27021 个角色标签，春物覆盖 11/12）在实际帧上只给到
> 0.03–0.14 的置信度，等于认不出；认得准的 WD-tagger（雪乃 0.99）词表里
> **连主角八幡都没有**。词表大的认不准，认得准的词表小。
> 而聚类这条路的词表不受限——它从这部番自己的素材里学。

### 第四步：确认六条数字相等

```bash
python -m pipeline.vindex status --anime <番>
#   片源 / 字幕索引 / 笔记 / 镜头表 / 角色在场 / 画面语义
```

**六条数字不相等就不许进每期循环。** 「先索引几集试试水，边做边补」是禁止的做法。

某次实测：完整片源 41 集、索引 6 集、笔记 31 集。原因是笔记里「完整视频只有 3 集」
那句话是几天前的真实情况，后来补下完了，但没人回头改笔记，也没人回头重建索引。
中间每一期都在 6 集的池子里挑素材，全程没有任何报错。

它的症状还会被误诊：有一期封面九张候选里挑不出一张主角占主位，当时归因于
「字幕检索有偏置」——偏置确实存在，但真正的放大器是池子只有应有的七分之一。
在一个假的素材边界里，调什么参数都是在调错的东西。

所以判据不能是「检索得到东西吗」，必须是「集数对得上吗」，前者永远为真。

### 第五步：选音色

参考干声放 `data/voice/reference/`，同一句话逐条试音：

```bash
for f in data/voice/reference/*.wav; do
  python -m pipeline.tts probe "随便一句带长句和短判断的话" \
      --ref "$f" --out "data/voice/probe/$(basename "$f")"
done
```

按重要性听三样：

1. **语速。** 同一句话在不同参考音下差得很多（实测 4.99s 到 8.23s，差 65%）。
   它直接决定成片长度，而时长与播放量负相关，是三样里唯一有数据支撑的。
2. **稳不稳。** 有没有电音、忽快忽慢、句尾发飘。
3. **音色。** 排最后。听的是「这个声音能不能撑 2–4 分钟口播」，不是「像不像原参考音」。

> **单句试音不能预测整篇语速。** 实测两条参考音在试音句上差 5%（6.52s vs 6.22s），
> 跑完整篇却反过来差 12%（122.5s vs 139.5s）。估成片长度必须看 `manifest.json` 的总时长。

选定后改 `config/voice.json` 的 `ref_audio`。字数带也跟着音色变，
`config/project.json` 的 `script.cpm` 要重测——实测同一音色在不同文风下差过 24%。

### 第六步：定 BGM 曲目表

```bash
python -m pipeline.bgm scan    <CD 目录>                    # 解 cue，列出 instrumental 轨
python -m pipeline.bgm extract <CD 目录> --anime <番>        # 切成独立 flac
python -m pipeline.bgm measure data/library/bgm/<番>/*.flac  # 量时长、响度、入声点
```

一部番定 3–5 首固定曲目，写进 `config/bgm.json`（给机器）和番剧笔记（给人）。
每期只在这几首里挑，不再回曲库翻。这样既省时间，也让同一套 BGM 反复出现形成听觉识别度。

> **扫曲库必须解 cue，不能只数文件。** 原声碟是拆好轨的（一首一个 flac），
> OP/ED 单曲碟是整轨镜像加 cue——一张碟只有一个 flac，四首歌全在里面。
> 按 flac 文件数扫曲库时六张单曲碟各自只显示为「一个文件」，整档 OP/ED 被漏掉，
> 而这一档恰恰是最强的：观众听见 OP 前奏就有情绪，劇伴给不了。

> **曲目表里没有实测 `lufs` 的曲子不许用**，`bgm.py` 会直接报错退出。
> 实测劇伴 -14.4…-18.1 LUFS，OP/ED 单曲伴奏 -7.1…-13.2 LUFS，极差 11 dB——
> 单曲是按打榜标准压过的，原声碟不是。

## 3.3 每期九步

### 01 选题 —— 人，周批量

`01-topic.md` 必须带齐这几项：

```markdown
番:   <番名>
模式: 驳论            # 驳论 = 通行说法不对；立论 = 作品里有个说不通的地方
张力: 弹幕里最常见的一句话是——大老师又自爆了。
锚点: S2E07 / S2E10 / S3E04
封面集: S3E12         # 可选，封面池不必局限于稿子引用过的集
```

**这一步真正要审的是「张力」那一句话。** 它是整条流水线里唯一的编辑判断，读它只要十秒，
但它决定这期片子有没有观点。张力必须在这一步定死并经人批准，不能留到写稿阶段由 agent
自行发明——那等于绕过唯一的人工关卡。写稿只校验、不更换。

### 02 写稿 —— Agent 约 3 分钟

调 `skills/write-script`：读上一期的稿子（为了不重样）→ 校验张力 → 查证剧情 →
挑一个与上期不同的**形状**写正文 → 切成 8–20 段，每段配一条 `查询` 和一条 `备选`。

> **2026-08-03 起这里不再有固定骨架。** 原先是「张力 → 判断 → 论据×3 → 公道话 →
> 转回 → 结论」八节表，三期稿子照着它写，结果三篇骨头一模一样、套话跨期复用。
> **写得足够具体的东西，模型都会照抄，与话题无关**——所以形状改成从张力里长，
> skill 只留判据不留模板。详见 `skills/write-script/SKILL.md`。

> **2026-08-04 又改了一次，方向反过来：少写「不许」，多写「必须有」。**
> 08-03 加的判据全是禁令，而**禁令的补集是均匀的**——三轮加禁令下来，
> 最新一期成了三期里句长最整齐的一篇（CV 0.34，人类样本 0.45–0.81），
> 机检全绿但人一听还是「每期一个样」。这次的改动是：拆掉制造均匀的门禁
> （`max_sentence` 40 焊死了长句，`min_breath` 是误诊），换成起伏类判据，
> 并给写稿加了三个正向动作——**捡料**（攒过量的具体材料，含不为论点服务的细节）、
> **超写再删**（先写 1.6 倍再删，套话信息量最低所以第一个出局）、
> **段落功能不许齐一**。量化依据在 `skills/write-script/BASELINE.md`。

```bash
python -m pipeline.check_script data/episodes/<本期>/02-script.md
```

机检覆盖：字数、时长估算、单句上限、**气口段上限、句长起伏、长句下限与短句配额**、
论文连接词、括号、引号、阿拉伯数字、模糊指代、**跨期套话**、**论据是否报菜名**、
剧情锚点数、查询是否重复、查询是否误写成画面构图。主观项（张力立不立得住、
公道话像不像反方、形状是否换过）机器判不了，脚本会明确提示留给人看。

**机检全过不代表能交**——上一期就是全绿而被判定机器味太浓。所以自检拆成两遍：
**先保真**（台词原文、说话人、季集号、数字，去味改写最容易破坏的就是这些），
**再去味**（念一遍、查解释句、查每段是不是都在收金句）。顺序不能反。

**`查询` 是机器接口，不是备注。** 它被原样送进字幕索引检索，所以要写成台词语义：
「角色承认自己一直在逃避」有效，「中景，逆光，樱花飘落」必然落空——索引建在字幕上，
字幕里没有构图信息。

> 机检里的「论文连接词」检查曾经误报：把「最后那一集」判成论文腔，
> 而那是时间指代。原因是关键词匹配不看位置。修法是要求这类词出现在句首或句读之后，
> 「最后」额外要求后面跟逗号。

> 「查询重复」这一条是后加的。排片是全局贪心、同一处画面整期只用一次，
> 所以两段共用一条查询时，第二段会静默退到明显更差的命中，而且不报 `no_match`。

### 03 配音 —— Agent 约 5–10 分钟机器时间

```bash
python -m pipeline.tts data/episodes/<本期>
```

逐段合成，保留段落边界，不整篇一次生成。每段音频的时长用 `ffprobe` 复核后写进
`03-audio/manifest.json`——这个时长是下一步排画面的唯一依据，不采信模型自报。

中断可直接重跑，已过的段落跳过；改了稿再跑只重做改动的段落，`--force` 强制全做。

**每段生成后用 Whisper 回读一遍与原文比对**，抓漏读、重复、跑飞。不过就换种子重生成，
三次仍不过就整体退出，不留坏音频。自回归 TTS 的典型失败不是报错，是静默地念错。

> **按句合成，不按段。** 实测语速与文本长度正相关（r=+0.613），因为模型对整句时长有
> 先验，文本一长就压着念。改成按句合成后标准差从 0.57 降到 0.46。

> **回读比对前会归一化，而归一化可能把缺陷一起抹掉。** 有一次 TTS 把中文引号念成了字
> （「谁更该"赢"」念成「谁更该非赢匪」），回读判 PASS——因为参考文本被归一化剥掉了
> 引号，多念出来的两个字只算两处插入，CER 7% 远在门槛下。修法是合成前用
> `tts.speakable` 剥掉纯书面符号，逗号句号破折号一律保留（它们控制停顿）。
>
> 这一例是靠人耳听出来的，没有任何机器检查报警。所以成片交人之前至少听一遍开头和
> 最长的那一段。凡是「先归一化再比对」的检查，都要问一句：被归一化掉的那部分，
> 会不会正是缺陷所在。

> **同音字要折叠。** 「她帮你，但她不让你欠她」被听成「他帮你…」，CER 30%，
> 双阈值一起越线，重试三次全一样，整期退出——而音频完全正确。他/她/它 同音，
> ASR 不产出能区分它们的信息。只折读音完全一致的字：的/得/地 不碰，
> 因为「得」有 dé、「地」有 dì，折了会掩盖真的念错。

### 04 素材检索排片 —— Agent 约 1 分钟

```bash
python -m pipeline.clips data/episodes/<本期>
```

每段的 `查询` 送进索引取 Top-24，然后**全局贪心分派**：把所有 (段, 画面, 分数) 三元组
摊平，按分数降序占坑，同一处画面整期只用一次。不按段落顺序分——那是先到先得，
会让后面真正引用某句台词的段落抢不到那句话的画面。

每段按音频真实时长填满，单个片段不短于 2.5 秒（太碎会闪）。

**顺序不可交换的原因**：字数估算与实际语速的偏差每段几百毫秒，单看无所谓，
二十段攒下来就是几秒，而且是渐进错位，越到后面画面与口播差得越远，全程不报错。

**检索落空时走查询阶梯**：`查询` → `备选` → 该段 `配音` 原文，逐级重试，
门槛 0.45 全程不动。加大的是找的力度，不是放低的标准。

**阶梯只救不比。** 上一级够格就到此为止，绝不因为下一级分数更高而换掉。
实测 21 段里配音原文在 11 段上分数最高，按分数取最优很诱人，但它会把已经对的段落弄坏：

| 段 | 查询字段 | 配音原文 | 实情 |
|---|---|---|---|
| 17 | 0.855（逐字引用一句台词） | 0.559 | 查询是精确引语，换成配音会换来一个不相干的镜头 |
| 4 | 0.506 | 0.750（配音全文就是一个人名） | 高分来自「有人说出她名字」，而那个镜头拍的是说话的人，不是她 |

**分数高不等于画面对。** 分数量的是「旁白文本与字幕文本的语义相似度」，
而我们要的是「这个镜头是否呈现旁白在讲的那一刻」，两者只在查询写成台词语义时才重合。

三级都不及格就写 `"status": "no_match"`，渲染阶段硬失败，交人处理，不自动降级。
自动塞一段空镜看着省事，实际是把「画文不符」藏起来。

#### 视觉索引接进来的两个通道

分镜可以声明这一段要什么，据此决定走哪条路（ADR-0003）。二选一，都不写就是上面的现状：

```markdown
画面：
  人物: 雪乃                   ← 台词检索照旧，但候选只留检测到她的镜头
  查询: 雪之下同学 你果然什么都做得很好啊

画面：
  场景: 黄昏时分空无一人的天台   ← 画面语义检索。**当前不可用，写了会当场报错**
```

> **`场景` 这一路没建成**（2026-08-04）。第 2 层探针跑完了：检索本身不差
> （10 条查询 7 条 Top-3 有真命中），**但门槛立不住**——绝对余弦、每查询 z 分、
> CLIP 原生 softmax 三种定法全失败，反例「太空中的宇宙飞船」的 softmax 概率
> 0.896 高过「学校走廊」的 0.689。根因是 CLIP 余弦没有绝对含义：能在一条查询内
> 排高低，答不了「这算不算命中」。证据见 ADR-0003 待实测 #4。

`人物` 修的正是上表段 4 那种错配：检索命中的是「谁说了这句话」，镜头就在说话人身上。

**两条铁律：**

1. **一段只走一个通道。** 不并跑、不取最高、不加权，两个字段都写会当场报错。
2. **分数只在自己的通道内排序，绝不跨通道比较。** 台词的 0.7 和画面的 0.7
   不是同一个量，长得像纯属巧合。

第 2 条在分派画面时也要守。全局贪心本来要比「哪一段更想要这处画面」，
而那正是跨通道比较，所以改成**显式的通道优先级：台词段先挑**——
它们要的是「那句话发生的那一刻」，具体且不可替换；画面段要的是氛围，可替换余地大。

**角色过滤是软的：过滤后为空就退回不过滤的结果。** 人脸检测对侧脸、背影、遮挡会漏，
「检测到 X」可信但「没检测到 X」不等于 X 不在场，一次漏检不该卡住整期。
封面那边反过来用硬过滤，理由见第 08 步。

> **加大 Top-K 救不了落空。** 结果是按分数降序的，top-1 低于门槛时第 25 名只会更低。
> 落空的绝大多数原因是查询写错了，不是素材不够——实测把片尾查询从
> 「角色转身走出教室」（画面描述）改成「时间差不多了 我该走了」（台词式），
> 分数从 0.446 涨到 0.747。

> **索引建之前要滤掉两类垃圾。** 一是 ASS 绘图指令（`\p1` 后面跟着的一长串坐标），
> 占了某一季索引单元的 34%；它的信号在 `{...}` override 标签里，而清洗函数会在过滤
> 之前把标签剥掉，所以判据必须在剥标签之前跑。二是 OP/ED 歌词和画面字，
> 它们语义最贴但画面完全不能用——有一段的两个片段都落在两集的同一个时间码上，
> 因为那是片尾 ED。按 ASS 的 style 名滤，那是字幕组自己声明的分类，
> 比时间窗和文风都可靠。

### 05 审时间码 —— 人 5 分钟

```bash
python -m pipeline.review data/episodes/<本期>              # 出 04-review.html
open data/episodes/<本期>/04-review.html
python -m pipeline.review data/episodes/<本期> --approve
```

**这是整条流水线唯一的人工关卡。** 一页 HTML，每段并排三样：这段口播在说什么、
画面长什么样、那一刻的字幕原文是什么。每个片段抽三帧（进点、中间、出点）——
只看中间帧会漏掉「前半段是对的人、后半段镜头切走了」，而那正是要抓的错。
`no_match` 的段落标红顶到眼前。

要抓的是**台词对了但画面不对**：索引建在字幕上，命中的是「谁说了什么」，
但那句话可能是画外音，镜头在拍别的。机器判不了，只有眼睛能抓。

> **`--approve` 必须是显式动作。** 让 `clips.py` 自动写 approved 版是最省事的做法，
> 也正是这一关曾经形同虚设的原因：有一期两个文件字节完全相同，
> 画面是检索直出、没过人眼就渲了，错配等成片看完才发现。

### 06 渲染 —— Agent 约 1.5 分钟

```bash
python -m pipeline.render data/episodes/<本期>
```

按时间码切片 → 统一中间格式（libx264 / yuv420p / 1920×1080 / 无音轨）→ 拼接 →
混 BGM → 烧字幕 → 响度归一，一趟出片。40 个片段、3 分钟成片实测 77 秒。
10bit 转 8bit 在切片这一步落地，两个平台的转码链对 10bit 支持不稳，而我们又不做调色。

**两道截取守卫强制执行，缺一不可：**

1. 切之前校验 `seek + duration <= 源时长`，不足立即失败
2. 切之后复核实际时长与请求值之差不超过 1 帧

> ffmpeg 在片段超出源片末尾时静默截断且不报错，检索命中集尾时必然踩到，
> 一旦踩到整条音画全线错位而无任何提示。这是已复现的产线杀手。
>
> **「1 帧」要按源片实际帧率现算，不许写死。** 番剧片源常见 23.976 / 24 / 29.97
> 三种，按 30fps 的 0.034 秒去卡，会把 23.976fps（一帧 0.0417 秒）的合格切片判成不合格。
> 容差从 `ffprobe` 读到的 `r_frame_rate` 算。

**字幕折行自己算，不指望 libass。** ASS 的 `WrapStyle` 依赖空格找断点，中文整句没有
空格就不折。断点取标点（逗号、顿号、分号、冒号、问号、叹号、破折号），
用贪心策略在放得下的断点里取最远的那个。

> 中文破折号是两个字符，必须等一对补全再断。
> 折行策略原先是「攒够半行才断」，那个 0.5 是魔法数，而且失败方式是错的：
> 不达标就整句放弃折行，而不折行比稍短的卡更糟。

**BGM 一期一到两首**：正文垫劇伴，最后 15–20 秒换 OP/ED 伴奏，等功率交叉 3 秒。
换曲点卡段落边界，不卡固定秒数。每首按 `config/bgm.json` 里的实测响度归一到
-26 LUFS，再用 `sidechaincompress` 以人声为触发做闪避。

> **固定音量系数是错的控制量。** 初版用 `volume=0.35`，那个数是对着一首 -16.9 LUFS
> 的曲子调出来的。换成 -7.1 LUFS 那首，BGM 会凭空大 9.8 dB 直接压过口播，
> 而且不报错，只会某一期突然特别吵，等发出去才发现。
> 所以控制量是「归一到目标响度」，不是「乘一个系数」。

> **闪避深度不能在句尾后 100ms 之内量**——释放时间还没走完，量到的是过程不是稳态。

### 07 质检 —— 机器约 40 秒

```bash
python -m pipeline.qc data/episodes/<本期>
```

11 项，不达标非零退出，不进人工环节：

- 成片时长落在 2–4 分钟
- 音画时长误差小于 0.5 秒；成片与排片一致
- 响度符合 EBU R128 目标 -16 LUFS；无 true peak 超过 -1 dBTP
- 无超过 0.5 秒的纯黑；无超过 2 秒的静音段
- 字幕：无空段、不超宽、每卡一行、不超高

> **字幕那四项查的是实际折行结果，不是「原文长度 ÷ 每行容量」。** 初版就是后者，
> 等于假设折行一定会发生；而 libass 对无空格的中文根本不折行，
> 于是 91 字的一段渲成一整行、两头切出画面，这条检查照样判 PASS。
> 检查项一旦测的不是真实产物，通过就毫无意义。

主观项（节奏、观感）不进门禁。它们的根在稿子和排片上，回第 02 / 05 步改，
不在成片上补救。

### 08 封面与标题 —— Agent 约 1 分钟

```bash
python -m pipeline.cover data/episodes/<本期>                     # 出池子 + 联系表
python -m pipeline.cover data/episodes/<本期> --pick 107,110,20    # 定 9 张
```

这一步不新增人工环节，选封面和选标题并进第 09 步，点一张图、点一条标题合计半分钟。

**候选帧从三处取：**

1. `04-clips.approved.json` 里实际用上的片段，每 0.5 秒抽一帧
2. 番剧笔记里本期锚点对应的名场面时间码——agent 从台词索引检索、人扫过一眼确认的时刻
3. `01-topic.md` 的 `封面集` 通篇每 12 秒抽一帧，跳过 OP/ED

> **第 3 路是被打脸打出来的。** 初版只有前两路，理由写在代码里：「只用片中出现过的
> 画面，否则是标题党」。结果九张候选里没有一张主角占主位——三张背影侧脸，
> 六张根本没有他，而这一期从头到尾讲的就是他。
>
> 根因是池子本身系统性地偏：前两路的帧都来自字幕检索命中的时刻，
> 而稿子引用的台词大多是别人说给主角听的，镜头自然在说话人身上。筛选救不了这个，
> 池子里就没有想要的东西。「否则是标题党」这条也用过头了：给一期讲主角的视频配主角的
> 正脸是名副其实，真正算标题党的是拿一场不相干的戏去暗示别的内容。

**机器只做这几件事，逐条都有明确判据：**

| 做什么 | 判据 |
|---|---|
| 剔掉转场帧、运动模糊 | 拉普拉斯方差 < 60，没有清晰边缘 |
| 剔掉黑场、过曝 | 平均亮度落在 40–215 之外 |
| （可选）剔掉没有本期主角的帧 | 视觉索引的角色在场判定。`01-topic.md` 写 `封面人物: 一色彩羽` 或加 `--character` 启用 |
| 同一个镜头只留一张 | 同集内相隔 < 6 秒算同一镜头；另加 dHash 抓不同时刻复现的同一画面 |
| 按位置铺开取样 | 2 个坑留给名场面，其余按段落号均分，每档取最清晰的一张 |

> **角色过滤排在去重之前**，顺序是要紧的：去重每个镜头只留最清晰的一张，
> 若先去重，一个「主角在场但不是最清晰那张」的镜头会先被邻居顶掉、再被角色过滤放行，
> 结果是这个镜头整个消失。
>
> 这一处用**硬过滤**（为空则失败），与排片那边的软过滤相反：从几千帧里挑 9 张，
> 高精度低召回正合适，误杀无所谓；而排片一段只有几个候选，误杀就没片可用了。
> 它**不违反**下面那条「机器不假装能判哪张有张力」——在不在场是准入门槛，
> 和清晰度、黑场同类，9 张候选依然不排序。

> **去重是最要紧的一道。** 按 0.5 秒抽帧，一个 4 秒的镜头出 8 张几乎一样的图。
> 初版只用感知哈希，结果九个候选里四个是同一场戏几秒之内的四张。
> dHash 对「同镜头内角色微动」不敏感——人物挪一点、口型变一下就能差出十几位；
> 放宽阈值又会误合并真正不同的镜头。镜头是时间上的连续区间，按时间判才对。

**候选之间没有排名，这是刻意的。** 试过两版打分，两版都把正确答案压掉了：

| 打分方式 | 结果 |
|---|---|
| 清晰度<sup>0.5</sup> × (0.5 + 饱和度) | 把一场关键对视压到第 5，因为它背景是淡色的 |
| 纯清晰度 | 选出运动服店的货架、图书室的书架，主角一个都没有 |

第二版暴露了根因：**拉普拉斯方差测的是「画面里有多少细节」，不是「画面有多好」。**
杂乱背景细节最多，按它排等于专挑最杂乱的画面，与封面要的「主体突出」正好相反。
清晰度是准入门槛，不是排序依据，两者不能混用。换掉它的不是更好的打分函数——
饱和度、中心细节、对比度都是自己发明的判据，没有数据支撑。正确做法是取一份有代表性的
样本交给人判。

**分工是三层，不是两层：**

| 层 | 谁 | 做什么 | 判据 |
|---|---|---|---|
| 1 | 机器 | 剔黑场/过曝/糊帧、去重、编号 | 有明确阈值 |
| 2 | agent | 看联系表，挑出符合本期主题的（谁在画面上、占不占主位） | 认人 + 读内容 |
| 3 | 人 | 从 9 张里定一张 | 审美 |

第 2 层的接口是**联系表**：`sheet-*.jpg`，6×5 一张、带编号，一张顶 30 次单张读取，
纯粹为省 token。agent 看完报编号给 `--pick`。不加 `--pick` 时退到机械铺开取样，
仍然出得了 9 张——agent 不在场时流程不断，只是选出来的不一定切题。

**标题**给 5 条候选，每条注明走的是哪个路子（下判断 / 反问 / 复述再打 / 剧情钩子 /
金句），好让人横向比而不是逐条读。原料取稿件的第 2 节（亮判断）和第 8 节（结论），
那两句本来就是全篇最锋利的判断。判据是金句式而非论文式，具体说就是
**这句话能不能脱离视频单独发出去**。

> `07-titles.md` 已填表就不再覆盖。封面常要重跑几次调取样，而标题和封面在同一个命令里出，
> 曾经这么把写好的标题冲掉过一次。

### 09 发布 —— 人 3 分钟

点一张封面、点一条标题，然后上传。**上传手动做，不自动化。**
在 `meta.md` 记下本期实际人类耗时。

## 3.4 测试与守卫

```bash
pytest        # 273 条，6 秒，不碰片源、模型、外置盘
```

测试只覆盖纯函数：字幕折行与分卡、排片时长水填、查询阶梯、cue 时间码、合成单元切分、
回读 CER、封面去重与铺开、配置降级、ASS style 与绘图过滤。**测的不是 API 形状，
是上面那些坑**——每条断言对应一个踩过的具体错误，注释里写着它当初怎么错的。

不为了提覆盖率去 mock 掉 ffmpeg 或模型。涉及媒体的正确性交给截取守卫和质检门禁在真跑时
兜，它们检查的是真实产物，mock 检查的是 mock。

写测试有两条自加的纪律：

1. **期望值先在实现上跑一遍，再写进断言。** 写排片测试时有一条想错了：以为某个边界必然
   判 short，实际它会往前拉起切点。代码是对的，期望是错的。照着「我以为它应该怎样」
   写断言，等于把错误期望固化成测试。这不等于「跑出什么就断言什么」——
   跑出来的值先要看懂为什么是这个值，说不通就是找到 bug 了。
2. **写完做变异检验：把被测行为故意改坏，看测试红不红。** 一条永远绿的断言和没有断言
   效果完全一样，但它会让人以为这块被覆盖了。这又是一种静默失败。

## 3.5 换一部番

1. 改 `config/project.json` 的 `anime.default`
2. 改 `anchor_words`。这是稿件机检判定「可指认剧情锚点」的具名场合词，逐番不同，
   不换的话锚点检查会永远判 0 处
3. 在 `config/bgm.json` 里加一组曲目，每首必须带实测 `lufs`
4. 在 `config/characters.json` 里加这部番的角色名表（中文名 ↔ 聚类贴的名字）
5. **重新标定镜头切分阈值**。画风、剪辑节奏逐番不同，直接沿用上一部的数不算实测
6. 重跑整个 Phase 0。索引目录按番隔离，`clips` 和 `subindex search` 都按番过滤

> **换成真人影视素材时，视觉索引的第 1 层要整块换掉**：动漫人脸检测器和 CCIP
> 都是动漫专用的。这是有意做成可插拔通道的原因——摘掉它不影响字幕检索和画面语义通道。

`skills/write-script/VOICE.md` 是**空模板**，里面没有可用的声音样本。它教你怎么从自己的
既有文稿里提炼一份，填好放 `VOICE.local.md`（不进 git）。不填也能出稿，但会是通用 AI 腔。
