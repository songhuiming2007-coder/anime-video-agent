# 需求交接：生产中撞到流水线 bug → ava 开工单 → coding agent 修

日期：2026-10-12
性质：**上位需求文档**，不是 spec。下游产物 = Implementation Spec。
对应 issues：D82。

---

## 0. 一句话方向

ava 受 Code Freeze 约束不能改 `pipeline/` 与 `config/`，撞到真 bug 时今天只能由人切到 coding agent、凭记忆复述现场。改成：**ava 经人确认写一份带现场的工单，人把工单交给 coding agent，修完 ava 知道从哪一步续跑。**

依据：EGOIST 制作期仅 2026-09-11–13 三天仓库就有 40 多个提交，多数是 tts / music / clips / qc 的边做边修。supercell 编年史（音乐占比更高、素材更杂）预计还会撞新边界。

---

## 1. 需求

### A. 开单工具（新工具，一律弹卡）

工单分两部分，**现场由系统采集，模型不能改**：

| 系统采集 | 模型填写 |
|---|---|
| 出错的命令、退出码、输出尾部（沿用现有密钥脱敏） | 现象 |
| 当前代码版本（HEAD）与是否有未提交改动 | 预期 |
| 期目录、会话、时间 | 最小复现 |
| | **为什么是代码 bug 而不是用法错误**（必填；模型常把参数写错当 bug，D53 即一例） |
| | 阻塞了哪一期的哪一步 |

卡上显示工单全文，人批了才落盘——这就是「经过确认」。

### B. 去重

开单前比对未关闭的工单：同一命令、同一报错首行 → 在原单上追加一次复现，不新开。

### C. 交接（第一阶段只做半自动）

桌面端上一键复制「给 coding agent 的那句话」（工单路径 + 一句指令），由人发给 coding agent。

**第一阶段不自动拉起 coding agent**：改流水线要先出方案、人批（全局红线与「大改动先 Plan Mode」）；生产 agent 自己拉起改代码的 agent，中间没人，Code Freeze 就形同虚设。等工单质量跑出来再考虑第二阶段（隔离分支里自动修、人来合）。

### D. 闭环

coding agent 修完在工单末尾写处理结果（提交号、状态、怎么续跑），并按惯例把它整理成 issues 表的正式条目。ava 开会话时看到本期有「已修」的工单，提醒人从卡住的那一步重跑。

---

## 2. 不做

- 第一阶段自动拉起 coding agent（理由见 1.C）。
- 让 ava 自己判定「是 bug」后直接落盘：一律经人卡。

## 3. 待人裁决

1. **工单存哪里。** 仓库是**公开**的（`songhuiming2007-coder/anime-video-agent`），工单里有输出原文、本机路径、期名，不能进 commit。候选：
   - 仓库内 gitignore 的目录（建议：T7 不插也能用，coding agent 工作目录就在仓库）；
   - `data/_tickets/`（在 T7 上，天然不进 git；`_` 前缀不进期列表）。
   修完后进 issues 表的是 coding agent 整理过的条目，不是工单原文。
2. 「复制给 coding agent」那个按钮属于界面改动：照 UI 规则先出截图方案，人选。
